# ADR 012: Prepare GitHub Pages publishing behind an independent approval gate

## Status

Accepted. Workflow preparation can be verified in pull requests. Public Pages
configuration and publication remain pending owner-controlled safeguards.

## Context

The production build already emits static files with relative URLs and browser
tests exercise the site at `/` and `/howlscene/`, with and without JavaScript.
The GitHub repository currently has no Pages site and no configured Actions
environment. The requested public routes are `/howlscene/`,
`/howlscene/editor/`, and `/howlscene/examples/william-elias/`.

The repository must not publish merely because a pull request is merged. The
deployment workflow also needs an independent human approval step before it can
write to the public Pages site.

## Options considered

| Option                                                                          | Benefits                                                                                       | Costs and risks                                                                                     |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Publish from a branch                                                           | Simple repository setting and familiar workflow                                                | Couples publication to branch contents; less explicit artifact verification and approval boundaries |
| Build a Pages artifact in Actions and deploy it through a protected environment | Reuses the production build, has an explicit artifact boundary, and supports reviewer approval | Requires repository/environment setup and a manual release dispatch                                 |
| Use an external static host                                                     | Can offer previews and host-specific controls                                                  | Adds a separate service and credentials without improving this static product's required behavior   |

## Decision

Use GitHub Pages' custom Actions workflow. Pull requests build the site,
exercise the production files at root and project paths, and package `dist` as a
Pages artifact. They never deploy. A manually dispatched run also builds and
tests the selected ref, but the deploy job runs only when all of these conditions
hold:

- The selected ref is `main`.
- The operator sets the `publish` dispatch input to true.
- The repository variable `HOWLSCENE_PAGES_ENABLED` is exactly `true`.
- Two distinct required reviewers approve sequential protected environments.

The two approval environments must each have a distinct single required
reviewer, prevent self-review, and be restricted to `main`. The `github-pages`
deployment environment is also restricted to `main`. The repository variable
remains unset until those protections and the GitHub Pages Actions source are
configured and verified.
The workflow deliberately does not call `actions/configure-pages`, which can
configure Pages as part of a run.

Actions are pinned to verified commit SHAs. The artifact is generated by the
same `npm run build` command as the application and tested with the existing
production browser scenario before packaging.

## Consequences

The workflow is fail-closed by default and creates no production deployment on
push or pull request. An administrator must configure Pages, both approval
environments, the deployment environment, and the repository variable; two
different reviewers must approve each manual deployment. Until that happens,
no live URL is claimed.

The workflow verifies generated output under `/howlscene/` locally in Chromium.
It does not prove GitHub's public CDN behavior or establish human usability,
accessibility, or release readiness.
